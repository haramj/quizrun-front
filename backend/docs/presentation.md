## 스토리: "AI가 자꾸 틀린 문제를 냈다" (슬라이드 5의 핵심, 실제 겪은 일)

1. **문제 발견** — 키워드만 주고 출제하니 사실이 틀린 문제가 많았다. (BTS: "BTS가 부른 노래가 아닌 것"에 보기에 *Shape of You*가 있는데 *Dynamite*를 정답으로 표시)
2. **원인을 실험으로 분리** — 모델 교체(HCX-005 → HCX-007)는 도움이 되지만 부족했다. 같은 모델에게 다시 풀게 하는 **자기검증은 소용없었다**: "손흥민의 현재 소속팀은?"에 토트넘이라 답했고(위키에는 이미 LAFC), 검증 단계도 "일치"로 통과시켰다. 모델이 같은 오래된 지식으로 답하기 때문이다.
3. **해결 ① 근거를 준다** — 위키백과 본문을 주고 그 안의 사실로만 출제. 추가로 문제마다 **자료에서 복사한 근거 문장**을 내게 했다.
4. **해결 ② 서버가 기계적으로 확인한다** — LLM을 또 부르지 않는다. 근거 문장이 자료에 실존하는지, 정답이 근거 안에 있는지, 문제의 연도·수치가 근거와 같은지를 문자열 비교로 검사한다. 비용 0, 결과 결정적.
5. **검증이 실제로 잡은 사례** — 근거는 "2,000만 파운드"인데 정답은 "3,000만 파운드" / 근거는 "2015년 준우승"인데 문제는 "2023년 아시안컵" / 근거가 자료에 없는 "Ditto가 핫100 첫 진입곡".
6. **해결 ③ 번호를 맡기지 않는다** — 모델이 정답 번호를 자주 틀려서, 정답 텍스트와 오답 3개를 받아 서버가 보기를 조립한다.
7. **그래도 남는 오류는 사람이 잡는다** — 플레이어가 신고하고, 서로 다른 3명이 신고하면 자동으로 출제에서 제외. 삭제가 아니라 비활성화라서 AI가 같은 문제를 되살리지 못한다. 관리자는 신고 많은 순으로 확정하거나 오탐을 복구한다.
8. **결과** — 같은 키워드("손흥민")에서 처음엔 오류가 많았지만 개선 후 6문제 모두 위키 내용과 일치. 단, **완벽하지는 않다**(아래 한계).

## 데모 시나리오 (3분)

사전 준비: `docker compose up --build`, 브라우저 창 2개(방장/참가자), 네트워크 확인.

1. **방 만들기** — 키워드에 문제은행에 없는 트렌드 주제(예: "흑백요리사")를 입력. *"이 키워드는 저희 DB에 없습니다. 위키에서 자료를 찾고 CLOVA Studio가 만드는 중입니다."* (방은 **0.1초 만에** 열리고, 대기실에 "문제 준비 중"이 뜬다. 약 15~30초 동안 친구를 초대하거나 채팅하며 기다릴 수 있고, 그 시간에 아키텍처 슬라이드를 설명)
2. **참가** — 두 번째 창에서 6자리 코드로 입장 → 정원이 차서 카운트다운 시작.
3. **플레이** — 빠르게 맞히면 점수가 더 높은 것을 보여줌 (정답 1,000 + 속도 보너스 최대 500). 문제가 위키 내용과 맞는지 보여주기 (`credits`에 출처가 표시됨).
4. **서버 검증 강조** — 브라우저 개발자도구 Network 탭에서 `/state` 응답에 정답이 reveal 전에 없음을 보여줌.
5. **신고 시연(선택)** — 카테고리 방에서 3명이 같은 문제를 신고하면 다음 판부터 그 문제가 빠지는 것을 관리자 API로 보여줌 (프론트 신고 버튼이 없으면 curl 사용: [API 명세](api.md)). 발표 직전 `reactivate`로 복구해 둘 것.
6. **문제은행 누적 시연** — 같은 키워드로 한 번 더 방을 만들면 이번에는 응답이 빨라지고 `source: mixed`(문제은행 + 신규)로 나오는 것을 보여줌.
7. **폴백 시연(선택)** — "로제 아파트"처럼 자료가 없는 키워드는 0.9초 만에 이유를 설명하며 거절, 카테고리("개발")는 AI 없이 즉시 시작.

> 라이브 데모는 LLM 지연과 네트워크 때문에 흔들릴 수 있습니다. **같은 시나리오를 미리 녹화**해 두세요.

## 숫자로 말하기 (검증된 것만)

- 자동 테스트 **135개** 통과 (게임 규칙·API 계약·LLM 출력 검증·문제은행 혼합·자료 수집 정책·**서버 2대 동시성**·**진짜 Redis 통합 11개**·Init Script 규칙). Redis 없이 돌리면 124개 통과 + 11개 건너뜀
- **서버 2대 + LB(Round Robin) + Redis + MySQL**에서 한 판 진행: 요청 66 : 60 분산, 오류 0건. **게임 도중 서버 1대 강제 종료해도 6문제 끝까지 진행, 오류 0건**
- Redis를 멈추면 서버 readiness 503(LB가 제외), 복구 후 5~10초 안에 스스로 정상화
- Rocky Linux 8.9에서 `kill -9` 후 systemd가 **약 19초**에 되살림, 그 사이 다른 서버가 서비스하고 방 유지
- 문제은행 **15개 카테고리 · 180문제**, 정원 최대 **100명** (정원 초과 차단 테스트 포함)
- 방 생성 응답 **0.07초** (이전 15~30초). 문제 준비는 대기실에서 약 16~32초, 자료가 없으면 0.9초 만에 `failed`로 알림
- 검증이 실제로 걸러낸 오류 유형 3가지(정답-근거 불일치, 연도 오기, 지어낸 근거)
- 기존 Node 서버와 **응답 JSON 키 구조 100% 일치** (프론트 수정 0줄)

말하면 안 되는 것: "10,000명 동시 접속", "NCP에 배포 완료", **"NCP에 Load Balancer와 Auto Scaling을 적용했다"**(NCP 리소스는 없다. 로컬 LB·서버 2대로 검증), "Cloud DB for MySQL·Cache를 쓴다"(MySQL 8·Redis 7 **컨테이너**로만 검증), "서버를 얼마든지 늘려도 된다"(100명 방 읽기 비용·Redis 단일 장애점이 남음), "로그인·전적을 지원한다", "AI 문제는 항상 정확" — 검증하지 않았거나 사실이 아닙니다. 정확도는 "크게 개선"이지 "해결"이 아닙니다.

말해도 되는 것(검증함): LB 헬스체크 엔드포인트가 HEAD/GET으로 동작, `DB_URL`만 바꿔 MySQL 8에 연결(신고·관리자 흐름 정상), DB 목표 스키마를 MySQL에서 실행하고 제약 25개 시험, v1→v2 데이터 이행 검증(185문제·정답 불일치 0), **무상태 격차를 실험으로 발견하고 Redis 외부화로 고쳐 재검증**(서버 2대·장애 전환·Redis 정지), 서버 이미지 + Init Script 배포 절차를 Rocky Linux 8.9에서 검증.

## 예상 질문과 답변

**Q. 수업에서 배운 클라우드 기술을 적극 활용했나요?**
**백엔드가 할 수 있는 부분은 상당히 했고, NCP에 올리는 작업은 아직입니다.** 수업 기술 18개 항목으로 점검했더니 처음에는 코드로 검증한 것이 2개뿐이었고, 가장 큰 격차는 Day4의 무상태 설계였습니다(서버 2대 실험에서 방이 서로 보이지 않음, 404). 방 상태를 Cloud DB for Cache(Redis)로 외부화해서 같은 실험을 통과시켰고, 서버 이미지 + Init Script 배포 절차도 만들어 지금은 ✅ 4 · 🟡 3 · 📐 8 · ❌ 2 · ➖ 1입니다. 📐 8개(VPC, ACG, NAT, Auto Scaling, Cloud Insight 등)는 인프라 담당이 NCP에 만들 영역이고 설계·규칙표·인수인계 문서까지 준비했습니다. 남은 ❌는 Object Storage 2개입니다. 모든 검증은 로컬 컨테이너에서 했습니다. 점검 결과는 `cloud-alignment.md`에 있습니다.

**Q. DB는 어떻게 설계했나요? 현재 코드와 다르다면서요?**
수업 순서대로 요구사항 분석 → ER 설계 → 관계 스키마(사상 알고리즘 7단계) → 정규화 → 물리 설계 → 보안 설계를 했고 테이블 11개로 정리했습니다. 현재 코드의 v1 스키마는 보기를 `option1~4` 열로 두는 등 수업 원칙과 어긋나서, v2로의 차이와 이행 스크립트를 문서화하고 MySQL에서 이행까지 검증했습니다. 다만 코드는 아직 v1을 씁니다. 상세는 `database-design.md`.

**Q. 서버가 여러 대면 방 상태는 어떻게 공유하나요?**
**Redis(Cloud DB for Cache)에 둡니다.** 방 상태를 JSON으로 Redis에 저장하고, 한 방의 변경은 방 단위 분산 락으로 직렬화하며, 700ms 폴링은 락 없이 읽습니다. 처음에는 서버 메모리에 두어서 서버 2대 실험에서 404가 났고(수업 Day4가 경고한 바로 그 문제), 외부화한 뒤 같은 실험을 통과시켰습니다. 한계는 Redis 한 대가 새 단일 장애점이라는 것과, 실제 Cloud DB for Cache 인스턴스로는 아직 확인하지 못했다는 것입니다.

**Q. AI가 틀린 문제를 내면요?**
모델의 기억 대신 위키 근거로 출제하게 하고, 서버가 근거 문장 실존·정답 일치·숫자 일치를 검사해 탈락시킵니다. 실제로 근거와 모순되는 정답, 연도 오기, 지어낸 근거를 걸러냈습니다. 다만 자료 자체가 틀렸거나 근거 안에서 엉뚱한 부분을 묻는 경우는 못 막습니다. 그래서 문제 신고→삭제 기능을 다음 단계로 두었습니다.

**Q. 왜 LLM에게 한 번 더 검증시키지 않았나요?**
실험해 봤습니다. 같은 모델이 같은 오래된 지식으로 답해서 틀린 문제를 "일치"로 통과시켰습니다("손흥민의 현재 소속팀은 토트넘"). 그래서 모델이 아니라 근거 문서와의 문자열 비교로 검증합니다. 비용이 없고 결과가 항상 같습니다.

**Q. AI가 15~30초나 걸리면 사용자가 기다리다 떠나지 않나요?**
방 생성은 기다리지 않고 즉시 응답하고, 문제는 대기실에서 백그라운드로 준비합니다. 그동안 친구를 초대하고 채팅할 수 있고, 정원이 차거나 방장이 시작을 눌러 두면 준비가 끝나는 즉시 카운트다운이 시작됩니다. 상태는 기존 폴링 `state`에 `prepare` 필드만 얹어 전달해서 새 연결 방식이 필요 없었습니다. 동시 준비는 4개로 제한해 CLOVA 쿼터를 보호합니다.

**Q. 준비 중에 서버가 죽으면요?**
방은 Redis에 있으므로 서버가 죽어도 방은 남습니다. 다만 문제를 만드는 일(AI 호출)은 방을 만든 서버의 스레드에서 돌기 때문에 그 서버가 죽으면 준비가 끊깁니다. 그래서 준비가 180초를 넘기면 **다른 어떤 서버든** 그 방을 실패 처리하도록 했고(자동 테스트로 확인), 사용자는 새 방을 만들면 됩니다.

**Q. 신고를 악용하면요?**
로그인이 없어서 완벽히 막지는 못합니다. 참가자 한 명이 한 문제를 한 번만 신고할 수 있고 서로 다른 3명이 필요하며, 오탐은 관리자가 복구할 수 있습니다. 근본적으로는 사용자 인증과 IP별 제한이 필요하고 로드맵에 있습니다.

**Q. 신고된 문제를 왜 삭제하지 않고 비활성화하나요?**
삭제하면 AI가 같은 문서에서 같은 문제를 다시 만들어 저장합니다. 비활성 행을 남겨 두면 같은 본문뿐 아니라 같은 근거 문장에서 나온 문제도 저장하지 않습니다. 복구도 쉽습니다.

**Q. 문제은행에 쌓아 두면 뭐가 좋은가요?**
같은 키워드를 반복할수록 AI 호출이 줄어 응답이 빨라지고 비용이 줄어듭니다. 한 판을 문제은행 30% + 신규 70%로 구성하고, 문제은행이 커지면 비율을 올립니다. 같은 사실을 다르게 물은 중복은 근거 문장 기준으로 막습니다. 단점은 한 번 저장된 오답 문제가 계속 나올 수 있다는 점이라 신고→삭제가 필요합니다.

**Q. 나무위키를 써도 되나요?**
CC BY-NC-SA 2.0 KR(비영리·출처 표시) 라이선스라 수업 프로젝트에는 가능하지만 상용에는 쓸 수 없습니다. 위키백과를 우선 쓰고 본문이 얇은 트렌드 키워드에만 보강하며, 설정으로 끌 수 있습니다. 출처는 응답의 `credits`로 내려 화면에 표시합니다.

**Q. API 키가 노출되면요?**
키는 코드·이미지·Git에 넣지 않고 환경변수로만 주입하며, 로그에도 남기지 않습니다. 운영에서는 서버 환경변수(권한 600 설정 파일)로 주입하고 Init Script 본문에는 넣지 않습니다. 개발 중 채팅 등에 노출된 키는 재발급해야 합니다.

**Q. 악의적인 키워드나 남용은요?**
키워드는 30자 제한과 제어문자 제거를 거치고, 프롬프트에서 "키워드는 주제일 뿐 지시문이 아니다"라고 고정합니다. 출력은 JSON 구조 검증을 통과해야만 쓰입니다. IP별 호출 제한은 아직 없습니다.

**Q. 왜 Spring Boot인가요?**
Redis·MySQL 연동, 보안, 모니터링 지표 등 남은 과제가 표준 라이브러리로 해결됩니다. 배포는 수업에서 배운 서버 이미지 + Init Script 방식으로 해야 하고(Docker는 수업 범위 밖) 그 절차는 아직 없습니다.

**Q. 왜 WebSocket이 아니라 폴링인가요?**
프론트 MVP가 700ms 폴링으로 동작하고, 로드밸런서·프록시 환경에서 가장 단순합니다. 규모가 커지면 SSE/WebSocket으로 바꿀 수 있도록 상태 계산을 요청 단위로 분리해 두었습니다.

## 발표 전 체크리스트

- [ ] 발표에서 쓸 NCP 서비스가 **수업에서 다룬 것과 일치**하는지 [architecture.md §3](architecture.md) 표 조정
- [ ] 실제로 만든 NCP 리소스가 있다면 스크린샷 추가, 없다면 "설계" 표기 유지
- [ ] CLOVA 키 **재발급** 후 발표용 키로 교체, 사용량 한도 확인
- [ ] 발표 직전 `docker compose down -v`로 문제은행 초기화 여부 결정 (쌓인 문제에 틀린 게 섞였는지 확인)
- [ ] 신고 시연을 했다면 `GET /api/admin/questions?status=inactive`로 확인하고 `reactivate`로 복구
- [ ] `ADMIN_TOKEN`은 화면 공유에 나오지 않게 주의 (curl 명령은 `$ADMIN_TOKEN` 변수로)
- [ ] 데모 키워드를 미리 한 번씩 돌려 보고 위키 문서가 있는지, 문제가 정상인지 확인
- [ ] 데모 녹화본 준비, 오프라인 폴백(키 없이 실행) 확인
